# Neighbourhood reliability and operator feedback

TownshipGo's focus is reliable everyday pedestrian journeys in a bounded neighbourhood, even when the user already knows their usual route. The resident interface retains its 2D/3D map, collapsible planning panel, walking profile and area selector.

## Features and entry points

| Capability | Where to use it | Evidence and behaviour |
| --- | --- | --- |
| Journey readiness | Plan a route, expand its summary | Presents travel time, recorded roof cover, continuous walking time without a verified rest, entrance/lift information and field evidence states. It is not an accessibility or safety guarantee. |
| My usual routes | Save usual route on a plan; open Saved | An optional monitor compares saved graph/field records with current area conditions, reports, repairs and guide expiry. Replan and save again to adopt a new baseline. Names, locations and settings stay in the browser. |
| Report to repair | Route help or a readiness barrier → Request a field check | Targets the actual path, crossing or facility and field. A check request is information, not a physical defect; it has no routing penalty or repair-cost estimate. The operator assigns responsibility, records a current field observation, reviews and resolves the request. Existing maintenance reports retain the checked/fixed workflow; record a fresh field observation when a physical condition is repaired. |
| Community local guides | Explore → Community routes | Draw or record public waypoints, select a purpose, preview network matching, trim private ends and submit for screening. Current guide-level field checks and public access hours govern navigation. Field-specific observations govern personal routing. Review history is appended, and guides expire. |
| Reachable places | Explore → Reachable places & comfort | Search by need, actual mapped connection, selected trip budget and profile. Add open-at-arrival, step-free, verified-only, roof-cover, public-access and fee filters. |
| Everyday errands | Explore → Plan errands | Choose 2–3 real mapped stops, dwell times and optional return to start. Choose a mapped place or let the app compare two nearby mapped candidates per purpose, then compare feasible stop orders on the graph. Budget includes walking, waits, rests, visits and return. Required rest intervals carry between legs; an errand is not assumed to supply a usable seat. |
| Comfort network | Reachable places → toilets, rest, water, covered waiting | Distinguishes mapped, checked and unknown amenities, access terms and hours. Any storm warning calls for appropriate indoor shelter or delaying the journey, not assuming a roofed footpath is adequate. |
| First and last mile | Explore → Transit; choose mapped station exit | Uses the actual access-point connection where one is mapped, with recorded level, step-free, lift and access-hour information. An approximate stop approach is labelled if no specific exit is available. |
| Walking together | Expand planning settings | Combine up to three companions with the user's own needs. Preserve all required conditions, use slowest pace, stricter slope/width and required rest characteristics. This overrides only the journey, not the personal profile. No companion identities are recorded. |
| Maintenance impact | Operator dashboard → Maintenance impact | Compare independent hypothetical repairs to checked cases or mapped barriers. Compute before/after directed, time-bounded walking catchments using actual path connections. Rank by additional reachable places and shorter mapped journeys. No simulation saves verification records, closes cases, or estimates real people served. |

## Sources and deployment

The added place purposes, access restrictions, fee tags, seating, levels and hours come from the **existing archived OpenStreetMap snapshots** in central KL (including Pasar Seni, Bangsar, Brickfields, Perdana Botanical Gardens, Pudu and Bukit Bintang) and UM campus. The deterministic enrichment script is `node scripts/enrich-neighbourhood-amenities.mjs`. It preserves source IDs, network geometry, attribution and the dataset revision. These are mapped attributes, not additional site observations. OSM data remains under ODbL; official directories, transit schedule snapshots, station plans and weather sources retain their existing attribution.

The server application uses PostgreSQL/PostGIS for public observations, maintenance cases, assignments and guide review history. The schema migration adds a field-check request field and guide purpose/history. Run the existing migration command when upgrading a deployed database. A field-check request can be reviewed with a current observation recorded for its target and requested field; a generic request requires a current target observation.

The GitHub Pages version uses public snapshots. Planning, route comparison, group settings, errands, routine storage, hypothetical repair analysis and local report/guide drafts work without a server. Device reports may remind the user to check a saved route, but they are not sent to an operator or treated as checked public reports. Publishing guides, changing the shared map, cross-device live observations and real repair tracking require the server application and authorised operator teams. The monitor refreshes public area feeds while the app is open; it is not a GPS tracker, background service or push-notification system.

Real defensibility comes from repeated, trustworthy field observations, a participating contributor community, assigned maintenance responsibility, transparent history and operator distribution. These features implement the workflow; they do not imply that a council, property operator, business or campus has agreed to use it. A useful pilot starts with a short, explicitly assigned corridor and field checks of its everyday destinations. Track the fraction of critical conditions with non-expired evidence, repeated usual-route use, time to verify and resolve reports, and reconnected mapped destinations after an observed repair. Validate the model against people walking the real corridor before making broader accessibility claims.

### Example model validation

For the archived Bangsar network, at 12:00 MYT on 25 November 2026, the 10-minute wheelchair-profile catchment from the mapped Bangsar start contains 11 mapped destinations/amenities. The hypothetical removal of recorded steps on segment `7332149513152` yields 14 (three additional mapped places). This is a reproducible network comparison, not a statement that a ramp has been designed, installed, field-checked or made safe. The real geometry and other restrictions are unchanged.
